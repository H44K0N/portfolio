How I build with AI

Most of the code in sjekka, stud, alfred and pulse was written by Claude, through Claude Code. I would rather say that plainly than let anyone assume I typed it all.

What I bring is the part that decides whether AI-written software is any good: knowing what I want, deciding how it should be put together, setting the rules it is built under, checking the result, and running it for real. This page describes that process.

Who does what

Mine

  • What gets built, and why
  • Requirements and hard constraints: cost, privacy, what must work offline
  • The shape of the architecture: what is its own app, what runs where, what talks to what
  • The call whenever the design forks
  • The standard a change has to meet before it ships
  • Testing on the real phone, with the real chest strap, in real exam weeks
  • The server, the domain and everything that runs on them

Claude's

  • Working out the detailed design inside that shape, and arguing back when it disagrees
  • Writing the code and the tests
  • Reviewing other agents' work
  • Routine operations on the server, inside rules I have set
  • Asking me when something is mine to decide

Every feature goes through the same steps, whether it takes an evening or a week.

The techniques that make it reliable

Write the brief first

Nothing starts from a one-line prompt. A project begins as a written brief: what it is for, what it must never do, what is undecided. The model has to ask me its open questions before it writes code, and my answers are recorded as decisions.

Example: for stud's audiobooks I set the rules up front. Free voices that run on my own server, about five minutes per chapter, written to be listened to, a quiz after each one.

Decide the architecture together, and have the last word

The model drafts a design and I push on it. The big structural choices are mine, and several of them overruled the first draft. The model fills in the detail and tells me when it thinks I am wrong; sometimes it is right.

Examples: my course material was going to be rebuilt as app screens, and I had it exposed as a read-only MCP server instead. stud and alfred are separate apps that read from each other because I did not want one large app. Alfred owns its own calendar with no outside integrations. Audiobook chapters are only written about ten ahead of where I am listening.

Put a contract between the parts

The app and the server agree on a documented API before either is built. That lets one agent build the Android side while another builds the backend, and it gives the review something exact to check against.

One orchestrator, several workers, separate clones

The strongest model plans and reviews. Cheaper models do the bulk of the writing. Each worker gets its own clone of the repository and its own branch, and its work comes back as a pull request, so two agents can never trample each other's files.

Nothing merges unreviewed

A pull request is checked out into a fresh clone and the tests are run there, not trusted from the agent's own report. Code that touches authentication or data is read line by line. Where it matters, the change is tried against a copy of real data first.

Example: a fresh-clone run caught tests that only failed between midnight in Oslo and midnight UTC.

Keep the core deterministic

Planning rules, schedules and scoring are ordinary code with ordinary tests. Language models get narrow jobs with typed inputs and outputs, and their answers are validated before anything is stored. Every app keeps working when the model is unreachable.

Example: sjekka rejects a receipt reading that does not fit its schema and retries it. Alfred was built to run with no model at all, and gained one afterwards.

Check generated content automatically, and cap the cost

Text written by a model for me to learn from goes through an automatic check and is rewritten if it fails. Spending has a monthly ceiling in code, and work is only generated a little ahead of where I actually am.

Look at every screen before the phone does

Each screen is rendered from fixed demo data into a contact sheet, including the dull states: offline, empty, error, sensor lost. I review the sheet, then install the build. The screenshots on this site come from those renders.

Write decisions down so they stick

What I decide, and feedback I give on how the work should be done, is saved to a small memory that every new session reads. I do not answer the same question twice, and a correction made once stays made.

Treat production as production

Deploys go through CI with a health check and automatic rollback. Containers run read-only with no extra privileges, nothing listens on a public port, and all traffic arrives through a Cloudflare tunnel. Private material is kept out of the repositories, and test data is a cleaned copy.

What went wrong, and what I changed

The first audiobook scripts all failed their own quality check. Six out of six first drafts needed a rewrite, which nearly doubled the cost per chapter. The cause was in the rules, not the model: the outlines asked for too much and the checker contradicted the writing instructions. Fixing the rules fixed the drafts.

Long status reports were noise. Agents are happy to report everything. I now ask for a few bullets of what changed and a numbered list of questions that need me, and nothing else.

An agent's "tests pass" is a claim, not a fact. That is why the review runs them again somewhere clean.

Why I work this way

The tools will keep getting better at writing code. The parts that stay human are deciding what is worth building, noticing when the result is wrong, and being responsible for it once it is running. Those are the parts I practise.
