How I build with AI

Claude wrote most of the code in sjekka, stud, alfred and pulse. I use Claude Code for that. I'd rather say so than have anyone think I typed it all myself.

My part is everything around the code. I decide what I want and how it should be put together. I set the rules it gets built under, I check the result, and I run it for real afterwards. This page is about how I do that.

Who does what

Me

  • What gets built, and why
  • The requirements and limits, like cost, privacy and what has to work offline
  • The overall architecture: what should be its own app, what runs where, and what talks to what
  • The decision when there are two ways to do something
  • How good a change has to be before it ships
  • Testing on my own phone, with the actual chest strap, during actual exam weeks
  • The server, the domain and what runs on them

Claude

  • The detailed design, within the architecture we agreed on
  • Telling me when it disagrees
  • Writing the code and the tests
  • Reviewing what other agents have written
  • Day-to-day work on the server, within rules I've set
  • Asking me when a decision is mine to make

What I do to make it reliable

I write a brief first

I don't start from a one-line prompt. Each project starts with a written brief that says what it's for, what it must never do, and what I haven't decided yet. Claude has to ask its questions before it writes any code, and my answers are saved as decisions.

For the audiobooks in stud, I set the rules before anything was built. Only free voices that run on my own server. About five minutes per chapter. Written for listening, with a quiz after each one.

We decide the architecture together, and I have the final say

Claude suggests a design and I push back on it. The big choices are mine, and several times I've gone against the first suggestion. Claude works out the details and tells me when it thinks I'm wrong. Sometimes it's right.

A few of my calls: the plan was to rebuild my course material as screens in the app, and I asked for a read-only MCP server instead. I wanted stud and alfred as two separate apps that read from each other. Alfred has its own calendar and doesn't connect to outside services. Audiobook chapters are only written about ten ahead of where I'm listening.

The app and the server agree on an API first

The API is written down before either side is built. Then one agent can build the Android app while another builds the backend. It also gives the review something exact to compare against.

One model plans, others write

The strongest model does the planning and the reviewing. Cheaper models write most of the code. Each of them gets its own clone of the repository and its own branch, and hands the work back as a pull request. That keeps two agents from overwriting each other's files.

Everything is reviewed before it's merged

The pull request is checked out in a fresh clone and the tests are run there. I don't go by what the agent says about its own tests. Code that deals with login or data is read line by line. If it matters enough, the change is tried on a copy of the real data first.

One fresh-clone run found tests that only failed between midnight in Oslo and midnight UTC.

The important logic is normal code

Planning, schedules and scoring are written as normal code with normal tests. The language model gets small jobs with a fixed input and output, and the answer is checked before it's saved. All the apps keep working when the model can't be reached.

sjekka throws out a receipt reading that doesn't fit the format and tries again. Alfred was first built with no model at all, and got one later.

Generated text is checked, and spending is capped

When a model writes something I'm going to study from, it goes through an automatic check and gets rewritten if it fails. There is a monthly spending limit in the code. Content is only generated a little ahead of where I am, so I don't pay for chapters I never get to.

I look at every screen before installing

Every screen is rendered from fixed demo data and put on one big sheet. That includes the boring ones, like offline, empty, error and lost sensor. I go through the sheet before I install the build on my phone. The screenshots on this site come from those sheets.

Decisions are written down

My decisions, and my feedback on how I want the work done, are saved in a small memory that each new session reads. It means I don't get asked the same thing twice, and I only have to correct something once.

Production is taken seriously

Deploys go through CI with a health check, and roll back automatically if it fails. The containers are read-only and run without extra privileges. Nothing listens on a public port, and all traffic comes in through a Cloudflare tunnel. Private material stays out of the repositories, and the test data is a cleaned copy.

Things that went wrong

The first audiobook scripts failed the quality check. All six first drafts had to be rewritten, and that almost doubled the cost per chapter. It turned out the problem was in the rules. The outlines asked for too much, and the checker disagreed with the writing instructions. Once the rules were changed, the drafts started passing.

The status reports got too long. An agent will tell you everything if you let it. Now I ask for a few bullets on what changed and a list of the questions I need to answer.

I stopped trusting "tests pass". At least from the agent that wrote the code. The review runs the tests again in a clean clone.

Why I work like this

AI tools keep getting better at writing code, and I expect that to continue. Someone still has to decide what's worth building, notice when the result is wrong, and take responsibility once it's running. That's what I'm trying to get good at.
